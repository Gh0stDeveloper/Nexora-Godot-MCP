# Security

Nexora Godot MCP can modify source files, scenes and project settings and can start local Godot processes. Treat it as privileged developer tooling.

## Baseline controls

- Keep the Godot editor bridge on loopback.
- Use a separate MCP credential and bridge secret.
- Keep the permission profile at `standard` for normal work.
- Keep unrestricted editor scripting disabled.
- Register/configure only project roots the user intends the AI to modify.
- Never expose the editor bridge directly to a LAN or the Internet.
- Never commit `.env` or `.nexora-godot/bridge.json`.
- Review generated code before shipping production builds.

## Authentication layers

The two trust boundaries deliberately use different credentials.

```text
MCP client
   │ Bearer/OAuth/local trust
   ▼
Gateway :8775
   │ independent bridge secret
   ▼
Godot bridge :9877
```

Compromising one credential should not automatically grant the other.

## Permission profiles

### safe

Read/inspection tools only.

Mutating scene, script, import, run-stop and export operations are blocked.

### standard

Default profile.

Allows structured project work inside the configured root.

It does not enable arbitrary editor script execution or a raw operating-system shell.

### unrestricted

Reserved for advanced opt-in capabilities.

Future arbitrary editor-side scripting requires both:

```env
NEXORA_GODOT_PERMISSION_PROFILE=unrestricted
NEXORA_GODOT_ALLOW_EDITOR_SCRIPT=true
```

OAuth deployments also require the `godot:script` scope.

## Path confinement

All user-provided paths pass through project-root normalization.

A path is rejected when its resolved filesystem location escapes:

```env
NEXORA_GODOT_PROJECT_ROOT
```

Godot bridge scene paths additionally require `res://` and reject traversal components.

Exports are also written beneath the configured project root in Phase A.

## Script safety

Phase A supports:

- reading `.gd` and `.cs`;
- creating scripts;
- revision-aware whole-file replacement.

`script_replace` requires the caller to provide the SHA-256 of the version it read. This prevents a stale AI operation from silently overwriting newer human work.

Direct node property editing explicitly blocks sensitive properties such as `script` and `owner`; dedicated tools will handle those concepts.

## CLI safety

The runner uses `asyncio.create_subprocess_exec`, not a shell.

The gateway creates the Godot argument list itself.

Normal tools cannot submit:

```text
bash -c ...
cmd.exe /c ...
powershell ...
arbitrary executable ...
```

## Runtime output

Managed stdout/stderr is bounded to avoid unlimited memory growth.

Runtime handles are explicit and generated by the server.

## Audit log

Default:

```text
./var/audit.jsonl
```

Sensitive fields such as secrets, tokens, passwords and API keys are replaced with `***`.

## Destructive operations

Destructive MCP tools use destructive annotations and explicit confirmation where practical.

Current example:

```text
node_delete(..., confirm=true)
```

The scene root cannot be deleted through `node_delete`.

## Bridge protocol

The bridge:

- binds to `127.0.0.1`;
- validates a 32+ character secret;
- accepts JSON objects only;
- validates operation names;
- limits batch size;
- rejects nested batches;
- returns structured errors.

## Remote deployments

If the MCP gateway is reachable beyond the local machine:

- use static bearer or OAuth mode;
- use TLS/private tunnels as appropriate;
- configure exact Host/Origin allowlists;
- add edge rate limiting when exposed to broader networks;
- do not expose port 9877.

## Credential incident response

If a credential is exposed:

1. stop remote ingress;
2. rotate the public/OAuth credential;
3. rotate the bridge secret;
4. rewrite the local bridge configuration;
5. inspect `var/audit.jsonl`;
6. inspect project source changes;
7. reconnect only after new credentials are active.
